# The Search Problem

"Our learners can't find lessons." The search analytics showed: 34% of searches returned zero results; 28% of searches with results led to no click-through. The lessons existed — they just weren't findable with keywords. A learner searching "how do databases handle multiple users writing at the same time" found nothing. The lesson "Transaction Isolation and MVCC" was directly relevant. "Keyword search can't bridge that gap," the Lead Data Engineer said. "We need semantic search."

# What Vector Embeddings Are

An embedding model converts text (or images, audio, code) into a dense vector of floating-point numbers — a position in a high-dimensional space.

```
"Transaction Isolation"  → [0.23, -0.41, 0.87, 0.12, ..., 0.55]  (1536 dims)
"Concurrent Writes"      → [0.19, -0.38, 0.91, 0.08, ..., 0.52]  (1536 dims)
"Banana"                 → [-0.82, 0.67, -0.23, 0.44, ..., -0.71] (1536 dims)

cosine_similarity("Transaction Isolation", "Concurrent Writes") = 0.94  (very similar)
cosine_similarity("Transaction Isolation", "Banana") = 0.03           (unrelated)
```

The embedding space encodes meaning. Semantically similar concepts are geometrically close — regardless of shared keywords.

```python
from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer('all-MiniLM-L6-v2')

# Embed lessons
lesson_texts = [
    "Transaction Isolation and MVCC — handling concurrent database writes",
    "PostgreSQL Indexing — B-tree and GiST index structures",
    "Data Encryption at Rest — AES-256 and key management"
]
lesson_embeddings = model.encode(lesson_texts)  # shape: (3, 384)

# Embed query
query = "how do databases handle multiple users writing at the same time"
query_embedding = model.encode(query)  # shape: (384,)

# Cosine similarities
similarities = np.dot(lesson_embeddings, query_embedding) / (
    np.linalg.norm(lesson_embeddings, axis=1) * np.linalg.norm(query_embedding)
)
# → [0.87, 0.31, 0.15]  — Transaction Isolation is most relevant
```

## Approximate Nearest Neighbour Search

```
Exact search (n=10M lessons, d=384):
  Compare query to all 10M vectors
  → 3.84 billion operations per query
  → ~15 seconds per query (unacceptable)

ANN with HNSW (Hierarchical Navigable Small World):
  Build multi-layer proximity graph at index time
  At query time: traverse from coarse to fine layers
  → O(log n) comparisons
  → ~2ms per query at 99% recall@10

IVF (Inverted File Index):
  Cluster vectors into k centroids at index time
  At query time: compare to n_probe nearest centroids only
  → Faster index build; slightly slower query than HNSW
  → Works with memory constraints (no full graph in RAM)
```

## Vector Database Options

| Technology | Type | Best For |
|---|---|---|
| pgvector | PostgreSQL extension | <5M vectors, existing PostgreSQL stack |
| Qdrant | Dedicated, open-source | Self-hosted, production scale |
| Weaviate | Dedicated + built-in embeddings | Multi-modal, built-in model serving |
| Pinecone | Managed SaaS | Zero-ops, enterprise scale |
| Milvus | Dedicated, open-source | Very large scale (billions of vectors) |
| ChromaDB | Embedded | Local development and prototyping |

## The RAG Pattern

Retrieval Augmented Generation extends an LLM with a searchable knowledge base.

```
Learner asks: "What's the difference between partitioning and sharding?"

Step 1: Embed the query
  query_vector = embed("What's the difference between partitioning and sharding?")

Step 2: Retrieve relevant context
  results = vector_db.search(query_vector, k=3)
  # Returns: ["de-sen-m2-03 (partitioning)", "de-sen-m2-02 (sharding)",
  #           "de-jun-m4-01 (database indexing)"]

Step 3: Augment the LLM prompt
  prompt = f"""
  Answer the learner's question using only the following lesson excerpts:
  
  [Lesson: Sharding — Splitting Data Across Nodes]
  {sharding_excerpt}
  
  [Lesson: Partitioning — Dividing Tables Within a Node]
  {partitioning_excerpt}
  
  Question: {learner_question}
  Answer:
  """

Step 4: Generate grounded answer
  llm.complete(prompt)
  → Explains partitioning vs sharding, citing specific lesson content
  → References accurate information from the retrieved lessons
  → Does NOT hallucinate technical details not in the retrieved content
```

## Embedding Pipeline Architecture

```
Batch embedding (lesson catalogue):
  dbt model outputs lesson content → Airflow DAG → 
  Batch embedding job (GPU or API) → 
  Insert into pgvector / Qdrant

Incremental update:
  New or updated lesson → trigger embedding computation → 
  Upsert vector in database (by lesson_id)
  Staleness SLA: lesson embedding updated within 1 hour of content change

Query serving:
  Learner search query → 
  Embed query (low latency: ~10ms) →
  Vector search (ANN): ~2ms →
  Return top-k lesson IDs → 
  Fetch lesson metadata from PostgreSQL →
  Return to user
```

## Common Mistakes

> **Vector Search as Keyword Search Replacement**
> Vector search is not always better than keyword search. For exact phrase matching ("de-sen-m2-03"), BM25 keyword search is better. For semantic queries, vector search wins. Best practice: hybrid search — combine keyword (BM25) with semantic (vector) using Reciprocal Rank Fusion.

> **Embedding Model Mismatch**
> The same embedding model must be used for indexing and querying. If you index with ada-002 and query with a different model, the vector space is different — results are garbage. Store the embedding model version with the vectors.

> **Static Index on Dynamic Content**
> Lesson content that changes without updating the embedding produces stale, misleading search results. Implement a content change trigger that recomputes embeddings within an agreed SLA.

## Mental Model

Think of vector embeddings as **GPS coordinates for meaning**. If Paris and Lyon are 400km apart in geographic space, "concurrent writes" and "transaction isolation" are similarly "close" in meaning space. A vector database is the GPS map — you can find concepts geographically near your starting point without knowing their exact names. A keyword search is like looking for a street by exact address — missing "Transaction Isolation and MVCC" when you searched "concurrent writes" is the equivalent of failing to find the right building because you didn't know the street name.

**Mini Summary**: Vector embeddings encode semantic meaning as positions in high-dimensional space — similar concepts are geometrically close. ANN algorithms (HNSW, IVF) make similarity search practical at scale (O(log n) vs O(n)). RAG extends LLMs with a vector knowledge base — retrieved context grounds generation, reducing hallucination. Options range from pgvector (small scale, PostgreSQL) to Pinecone (managed, large scale). Hybrid search (BM25 + vector) outperforms either alone. Always use the same embedding model for indexing and querying.

# Integration

**Mathematics**: Vector similarity search is a geometric problem in R^d (d-dimensional Euclidean space). Cosine similarity measures the angle between vectors: cos(θ) = (A · B)/(||A|| × ||B||) ∈ [-1, 1]. HNSW operates on the mathematical structure of **small-world networks** — graphs where the average path length between any two nodes is O(log n) even for large n (Watts-Strogatz theorem). The layered HNSW structure creates a hierarchy of increasingly sparse small-world graphs. A query traverses from the sparsest (longest-range connections) to the densest (local connections), bounding search complexity to O(log n) — the mathematical reason ANN at scale is tractable. The probability distribution of cosine similarities for random high-dimensional vectors is approximately normal with mean 0 and variance 1/d — explaining why dimensionality reduction techniques (PCA, UMAP) improve separation of meaningful clusters in embedding spaces.

**Sciences**: Vector embeddings learn the same representational structure that the brain uses. **Sparse coding** in neuroscience (Olshausen and Field, 1996) shows that the visual cortex represents images as sparse, distributed activations across neurons — analogous to dense vector embeddings representing text semantics. The "grandmother cell" hypothesis (one neuron for one concept) was replaced by distributed representation evidence — the same distributed representation that LLM embeddings implement. The mathematical proximity of embeddings (cosine similarity) mirrors neural coactivation patterns: neurons that fire together wire together (Hebb's rule), and concepts that appear in similar contexts have similar activation patterns — encoded geometrically in the embedding space.
