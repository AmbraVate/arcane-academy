# Hook

Every row in every table needs an address. Without a unique identifier for each row, the database cannot distinguish between two customers named "John Smith", two products with the same name, or two orders placed at the same moment. The primary key is that address — the one guaranteed way to point at any single row and say: this one.

Primary keys are also the foundation of the entire relational model. Foreign keys — the mechanism that links tables together — reference primary keys. Without well-designed primary keys, the web of relationships between your tables cannot be built.

# Lore Introduction

"Every record in this archive needs a unique reference number," Master Selvaris said, opening a thick registry to a page showing three entries all labelled "Aldric the Smith." "Three different merchants. Same name. No way to tell them apart." She tapped the page. "When we tried to update the tax records for one Aldric, we changed all three." She closed the book. "Every record needs a number that belongs to it alone — one that never duplicates, never disappears, never changes. We call it the primary key. It is the record's identity in this archive, independent of everything else it contains."

# Core Learning

## Concept Introduction

### Definition

A **primary key** is a column (or combination of columns) whose values:
1. **Uniquely identify** each row — no two rows can share the same primary key value
2. **Are never null** — every row must have an identity

```sql
CREATE TABLE customers (
    customer_id   INT          NOT NULL,
    first_name    VARCHAR(100) NOT NULL,
    email         VARCHAR(255) NOT NULL,
    CONSTRAINT pk_customers PRIMARY KEY (customer_id)
);

-- Shorthand (most common):
CREATE TABLE customers (
    customer_id   INT          PRIMARY KEY,
    first_name    VARCHAR(100) NOT NULL,
    email         VARCHAR(255) NOT NULL
);
```

### Natural Keys vs Surrogate Keys

| Type | Description | Example | Risk |
|------|-------------|---------|------|
| **Natural key** | A real-world identifier with inherent meaning | Email address, ISBN, passport number | Can change; may not be truly unique; external dependency |
| **Surrogate key** | A system-generated identifier with no real-world meaning | Auto-increment integer, UUID | None — stable by design |

```sql
-- Natural key: risky
CREATE TABLE books (
    isbn         CHAR(13) PRIMARY KEY,  -- what if ISBN is corrected?
    title        VARCHAR(300)
);

-- Surrogate key: stable
CREATE TABLE books (
    book_id      INT PRIMARY KEY,       -- means nothing outside the database
    isbn         CHAR(13) UNIQUE,       -- still unique, but not the PK
    title        VARCHAR(300)
);
```

### Auto-Increment Integers

Most databases provide a mechanism to automatically generate incrementing integer primary keys:

```sql
-- PostgreSQL / standard SQL
CREATE TABLE orders (
    order_id  INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    ...
);

-- MySQL / MariaDB
CREATE TABLE orders (
    order_id  INT AUTO_INCREMENT PRIMARY KEY,
    ...
);
```

The database assigns the next integer automatically when a row is inserted. The values are simple, small, fast to index, and never require manual management.

### Composite Primary Keys

Sometimes no single column uniquely identifies a row, but a *combination* of columns does:

```sql
-- A student can enrol in many courses; a course can have many students
-- The combination (student_id + course_id) uniquely identifies each enrolment
CREATE TABLE enrolments (
    student_id  INT NOT NULL,
    course_id   INT NOT NULL,
    enrolled_at DATE NOT NULL,
    PRIMARY KEY (student_id, course_id)
);
```

## Why It Matters

Primary keys are the anchor of the relational model:

- **Row addressability**: You can always retrieve exactly one specific row with `WHERE customer_id = 42`
- **Referential integrity**: Foreign keys in other tables reference primary keys to create relationships
- **Performance**: Primary keys are automatically indexed — lookups by primary key are the fastest possible query
- **Data integrity**: The UNIQUE + NOT NULL guarantee prevents duplicate or unidentifiable rows at the database level

## Common Mistakes

- **No primary key at all**: Without a primary key, rows cannot be uniquely addressed, and the database permits exact duplicate rows (creating ghost data).
- **Using a mutable value as PK**: Email, username, phone number — all can change. When a primary key changes, every foreign key referencing it must be updated too.
- **Composite PKs where a surrogate would do**: A simple `id INT PRIMARY KEY` is cleaner than a four-column composite PK in most cases.
- **Re-using deleted IDs**: Gaps in auto-increment sequences are normal and harmless. Attempting to re-use deleted IDs creates confusion and potential security issues.

## Mental Model

Think of the primary key as the book's catalogue number in a library. Every book has a unique number stamped on its spine. If a book is moved to a different shelf, its title may be displayed differently, its author may be renamed (posthumously), but its catalogue number never changes. It is the permanent, unique address of that physical book. Everything — the library system, the borrowing records, the reservations — references that catalogue number. The primary key is exactly this for every row in your database.

## Mini Summary

- ✔ Every table needs a primary key: unique + not null
- ✔ Surrogate keys (auto-increment integers) are stable, simple, and widely preferred
- ✔ Natural keys carry risk — external values can change or be corrected
- ✔ Composite PKs are valid when no single column uniquely identifies a row
- ✔ Primary keys are automatically indexed and form the basis for table relationships

# Integration

**Mathematics**: A primary key implements the mathematical concept of an injective function (one-to-one mapping). In set theory, a primary key is a function from the set of all rows in a table to a set of unique identifier values, where every row maps to exactly one key value and no two rows map to the same key value. This is precisely the definition of injection. The NOT NULL constraint ensures the function is total (defined for every input). The relational model's requirement for primary keys is therefore a statement about the mathematical structure of valid relations.

**Sciences (Genetics)**: Every organism's DNA can be identified by a unique sequence — a biological primary key of extraordinary complexity. But in practice, geneticists often use simpler surrogate identifiers (specimen IDs, accession numbers) because DNA sequences are unwieldy to work with directly as identifiers, just as engineers prefer integer surrogate keys to email addresses. The parallel illustrates why primary key design is not about finding the "most accurate" identifier but about balancing uniqueness, stability, and practicality.
